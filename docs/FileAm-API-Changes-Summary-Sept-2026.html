1. Standard response envelope

All mobile routes return:

{
  "status": true,
  "message": "Human-readable message",
  "data": { /* payload */ }
}

Errors: status: false, HTTP 4xx/5xx, message explains the failure. Undo conflicts return 409.

2. CIT/PIT monthly computation fix

Behavior change Source: CIT_PIT_Bug_Report.pdf

CIT and PIT now use only the requested month's sales and expenses (voided/reversed rows excluded). Each month returns a distinct value; multi-month ranges sum per-month amounts.

MethodPathChange
GET /tax-computation?period=YYYY-MM data.cit.periodAmount and data.pit.periodAmount are monthly estimates from that month's books.
Optional: range=month|quarter|year — CIT/PIT summed across included months.
GET /tax-payables?period=YYYY-MM&page=1&limit=20 CIT/PIT payable rows sync per book month (not December-only).
data.totals.cit / data.totals.pit match the requested period computation.

5. Sales & expense undo

Changed New routes Source: SALES_AND_EXPENSE_UNDO_API.pdf

MethodPathTypeDescription
GET/sales?status=...ChangedStatus adds Voided, Reversed. Counts add voided, reversed. Summary excludes undone.
GET/sales/:idChangedAdds undo when voided/reversed
GET/sales/:id/undoNewReturns action backend will run
POST/sales/:id/undoNewExecutes void or reverse
GET/expenses?status=...ChangedSame status/count rules as sales
GET/expenses/:idChangedAdds undo
GET/expenses/:id/undoNewUndo check
POST/expenses/:id/undoNewExecute undo (409 if converted to asset)

GET /sales/:id/undo — response

{ "status": true, "message": "Sale undo check", "data": { "action": "void" | "reverse" } }

POST /sales/:id/undo — request

{ "reason": "Created by mistake" | "Duplicate sale" | "Wrong amount" | "Wrong customer" | "Wrong product" | "Wrong date" | "Sale cancelled" | "Other" }

POST /sales/:id/undo — response

{
  "status": true,
  "message": "Sale undone",
  "data": {
    "action": "void" | "reverse",
    "status": "voided" | "reversed",
    "data": { /* full SaleDetail with undo populated */ }
  }
}

POST /expenses/:id/undo — request reasons

"Created by mistake" | "Duplicate expense" | "Wrong amount" | "Wrong expense category" | "Wrong supplier" | "Wrong date" | "Expense cancelled" | "Other"

Detail undo block (sales & expenses)

"undo": {
  "at": "2026-09-07T11:30:00.000Z",
  "reason": "Wrong amount",
  "reversingEntry": { "id": "ledger-tx-uuid", "date": "2026-09-07" } | null
}

Rules: No ledger → void. Ledger posted → reverse. Voided/reversed records cannot be edited, paid, or undone again.

7. Liability undo

Changed New routes Source: LIABILITY_UNDO_API.pdf

MethodPathTypeDescription
GET/liabilities?status=all|Voided|ReversedChangedcounts, recordStatus, undo on rows
GET/liabilities/:idChangedrecordStatus, undo when undone
GET/liabilities/repayments?status=all|ReversedChangedcounts, recordStatus, undo
GET/liabilities/:id/undoNew409 if live repayments exist
POST/liabilities/:id/undoNewVoid or reverse financing liability
GET/liabilities/repayments/:id/undoNewAlways reverse
POST/liabilities/repayments/:id/undoNewReverse repayment; restores parent balance

POST /liabilities/:id/undo — request

{ "reason": "Created by mistake" | "Duplicate liability" | "Wrong amount" | "Wrong creditor" | "Wrong date" | "Not a business liability" | "Other" }

Undo response envelope (liabilities)

{
  "data": {
    "action": "void" | "reverse",
    "status": "voided" | "reversed",
    "data": { /* LiabilityDetail or RepaymentDetail */ }
  }
}

recordStatus is sibling to payment status (ACTIVE | voided | reversed). Undo repayments before undoing parent liability.

10. Employee & employer prospective terms

Behavior change Source: EMPLOYEE_AND_EMPLOYER_PROSPECTIVE_TERMS.pdf

No new routes. PATCH behaviour changes only. Calendar uses Africa/Lagos.

MethodPathChange
PATCH/employees/:idSalary/relief changes apply from effectiveMonth (current Lagos month, or next if current PAYE is PAID/COMPLETED). Frozen payroll months never recompute.
PATCH/employers/:idRemuneration changes prospective; past income-history rows immutable once frozen.
GET/payee?period=YYYY-MMPast closed periods return frozen snapshots after PATCH.
GET/employers/:id/income-history?year=YYYYPast months frozen; current month may remain projection.

Request/response payloads for PATCH are unchanged. Annual totals use frozen months + open remainder (not 12 × new salary).

11. Shared undo types

type RecordUndoAction = "void" | "reverse"
type RecordUndoStatus = "voided" | "reversed"
type RecordUndo = {
  at: string          // ISO datetime
  reason: string | null
  reversingEntry?: { id: string; date: string } | null  // null after void
}
type UndoCheckResponse = { action: RecordUndoAction }
type UndoResponse<T> = { action: RecordUndoAction; status: RecordUndoStatus; data: T }
